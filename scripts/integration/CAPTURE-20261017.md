### Pointer corrections (after actual pilot 3, not yet executed)

Pilot 3 showed every 390 cell reporting `pointer: coarse` on its first state and `false` on every state after a click. An independent navigation (`result-error`) reported `true` again. The context options were correct (`isMobile`, `hasTouch`, DPR 2). Playwright's `locator.click()` sends mouse input even when the context has `hasTouch`. The old receipt measured pointer media only before the screenshots, so it couldn't tell whether the click or the full-page shot changed it. Changes:

1. **One activation helper** (`activate`): touch cells use `locator.tap()`, desktop cells use `locator.click()`. Every journey, state and video activation goes through it: home, planner (preset, reservation, Next, food, airport listbox), result tabs, tours (refund, booking CTA, calendar day and next month, Next) and charter (cards, Next, T1, Proceed to Pay). The consent box goes through `tick`: desktop keeps `check()`; touch taps it only if it's unticked, then requires `checked`. Typing and selection values are unchanged, and so are the required selectors and assertions. There are no `dispatchEvent` or evaluated clicks. The only remaining mouse or hover input is desktop-only: the desktop held press, and `cta.hover()` when the cell has no touch.
2. **Touch held press** (see Videos): CDP `touchStart` then `touchCancel`, never `touchEnd`.
3. **Pointer media diagnostic**: `pointer` = `{coarse, fine, hover, maxTouchPoints, vw, vh, dpr}`, read with `matchMedia`/`navigator` and never overridden. It's recorded per state at `beforeShot`, `afterViewport` and `afterFull`. Per cell, `pointer.firstActivation` records the state, input type and the snapshot before and after the cell's first activation. Video cells also record `pointer.videoEnd`. Any snapshot where `coarse`/`fine` doesn't match the cell (touch: coarse true, fine false; desktop: the reverse), or that couldn't be read, adds `pointer-media-unverified` and makes the state or video `unverified`, never `captured`. The frame is kept. No media emulation, Chromium flag or product CSS was changed.
4. **Charter quote and payment framing**: see `charter-quote` and `charter-payment-config-error` below. Both are pending an actual run.

### Full-page capture without `captureBeyondViewport` (after actual pilot 4)

Pilot 4 (`20261018-164946-capture-pilot-62a8dc40`) narrowed the drift down to the full-page shot. In 390 cells, `beforeShot` and `afterViewport` read coarse, not fine, no hover, `maxTouchPoints` 1. Straight after the first `fullPage` screenshot they read fine, hover, `maxTouchPoints` 256, and that held through later taps. Desktop cells also went to 256 after a full shot. A fresh `goto` reset it. Installed Playwright 1.62.1 (`coreBundle.js` `screenshotPage` → `takeScreenshot`) doesn't resize anything for `fullPage`. It sends one `Page.captureScreenshot` with a document clip and `captureBeyondViewport: true`. The viewport shot sends the same call with `captureBeyondViewport: false`, and it left pointer media alone. So the drift comes from Chromium's own beyond-viewport capture path. Inferred from the timing, not observed directly: that path changes pointer/touch settings before it renders, so the old full PNGs may have been drawn with desktop pointer media. A raw CDP call with `captureBeyondViewport` plus an explicit clip is exactly what Playwright already sends, so it wouldn't help.

`<state>.full.png` is now built by `stitchedFullPage`. It scrolls the window across the document and takes one real `Page.captureScreenshot{captureBeyondViewport: false}` per viewport through a CDP session. That's the same kind of call as the viewport shot. Each tile is decoded and placed losslessly at its scroll offset × DPR in one PNG. Nothing is generated or resampled. Viewport size, DPR, `isMobile`/`hasTouch`, the browser profile and launch args don't change, and nothing in media, `navigator`, CSS or Chromium flags is overridden. Caret hiding is the same as Playwright's (`caret-color: transparent !important` inline on inputs, restored afterwards). Scroll position and caret are restored, and the session is detached. Any of the following fails the shot as `screenshot-error` and writes no file: a tile error, a tile size that isn't viewport × DPR, a pinch-zoom scale other than 1, a gap in coverage, an image over 512 MB, a failed restore, or a failed detach. The receipt's `fullPage` records the method, tile count, CSS size, height after scrolling, viewport and DPR. The existing `afterFull` probe still checks pointer media after every full shot.

Raster scale fix (after pilot `20261018-170514-capture-pilot-8652674b`): that run was clean on pointer media and captured all desktop cells, but every phone full shot (22) failed with `tile 390x844 != viewport 390x844@2`. A raw CDP `Page.captureScreenshot` with a `clip` rasterises at `clip.scale` device px per CSS px and doesn't apply the emulated DPR. Tiles now request `clip.scale = devicePixelRatio`: a real 2x Chromium raster on phones (780×1688 at 390), unchanged 1x on desktop. The strict tile-size check stays, and nothing is resized or resampled. The receipt's `fullPage` also records `rasterScale` and `tilePx`.

Pilot `20261018-170929-capture-pilot-4efb5056` (exit 0): 12/12 cells captured, 0 failures, 0 unverified, 0 screenshot errors, 138 PNGs. Phone tiles are 780×1688 at `rasterScale` 2, desktop tiles 1440×1000 at 1. Pointer media held on every phone probe (coarse, not fine, no hover, `maxTouchPoints` 1). No WebSockets, no console errors, all 8 charter framings `ok`, guard clean, source provenance unchanged. **Open issue, not fixed:** after each phone full shot, `afterFull.dpr` reads 1. The next state's `beforeShot` and `metrics.devicePixelRatio` also read 1 until the next Playwright viewport shot puts it back to 2. The earlier `scale: 1` run (`8652674b`) shows the same counts (planner 2/8, charter 6/11, result 1/4 phone states with DPR 1 before the shot). So Chromium's clip path causes it, not the scale change. It means the 2x tiles are probably drawn with layout at DPR 1 and a 2x page scale, so DPR-dependent resources (`srcset`, `resolution` queries) may be 1x. This hasn't been shown to be a true DPR-2 raster. The stitch doesn't check DPR after a capture; neither do the pointer probes. Desktop reports `maxTouchPoints` 256 from the first `beforeShot` in both runs, before any full shot.

Limits: `position: fixed`/`sticky` elements (top bar, bottom nav, sticky CTA) appear once per tile, not once per page. Scroll-driven UI shows the state it had at each tile's offset. Content that loads or grows while scrolling is cut at the height measured first (`heightAfter` shows it). Only window scrolling is covered; inner scroll containers show their current scroll position only. This is still Chromium emulation, not a physical device, and none of it is a visual PASS.

## Offline Vite config (different from `npm run build`)

The config sets `PRERENDER=0` and then loads `./vite.config.ts` through `loadConfigFromFile`, so the Puppeteer prerender plugin is never created. It then does the following:

- Deletes `server.proxy` and `preview.proxy`. A deep merge would keep the `/api` → `https://cocotripkr.com` proxy, so the delete is explicit.
- Sets `envFile: false` and points `envDir` at a directory that doesn't exist (`scripts/integration/.no-env-20261017`).
- Forces `host 127.0.0.1` with the required numeric `COCOTRIP_OFFLINE_PORT`, plus `strictPort: true`, `open: false` and `hmr: false` (no dev WebSocket).
- Adds a server middleware that answers `/api/*` with `503 OFFLINE_LOCAL_API_BLOCKED`. In dev, `api/_shared/*.js` source modules still pass through, same as the original bypass.
- Injects synthetic public Firebase placeholders (`offline-synthetic-*`) via `define`. Without them, `firebase/auth` throws `auth/invalid-api-key` at import. `tests/charter-local-server.mjs` uses the same approach.
- Writes build output to `dist-offline-20261017/`, not `dist/`.

`configResolved` refuses to start if any of these holds:

- a proxy is present
- `envFile !== false`
- **envDir check fails.** `false` is accepted **only** when `envFile === false`. The reviewer observed this in the Vite 7.3.6 source: `envFile:false` resolves `envDir` to `false`. I couldn't re-inspect it because this worktree has no `node_modules`. A string envDir must resolve to the offline directory, and that directory must not exist or contain any `.env*` file.
- **any** `VITE_*` key reached `resolved.env`, from a file or from the process env
- wrong host/port, `strictPort`, or `open`
- HMR is on
- prerender is on

Only key names are printed, never values. The Vitest config uses the same envDir/envFile rule plus the env-key and proxy checks.

The harness clicks the first day that the component leaves enabled (cutoff and blocked days are disabled by the app) at least 7 days after KST today, moving at most two months forward. The day comes from react-day-picker v9's `td[data-day]`. This attribute is assumed from the library and hasn't been observed in this build; if it's missing, the state errors.
- `tour-booking-step1-date`: Escape closes only the calendar (the dialog must stay open). The trigger must show the picked ISO date, and Next must be exactly one and enabled. Pax and add-ons stay at their defaults.
- `tour-booking-step2-blank`: Next → Step 2 (the header must show the localized Step 2 title). Every text input/textarea must be empty and every checkbox unticked. Exactly one disabled "fill in all required fields" button stands where PayPal would be, and the footer text with the auto-cancel notice is recorded. Nothing is typed, no address is searched, no terms are ticked and nothing is paid. The dialog is then closed with Escape.
- The only offline boundary in this flow is the declared Firestore abort (`fetchMonthAvailability`, which falls back to the static availability). No API fixture, stub or auth fixture was added.

Sequential journeys (planner, charter, the result tabs) stop at the first failed state. The failed state is still captured, so the visible error or loading screen is kept. Later states are listed as `not-reached`.

### Videos (`--group video`)

There are two representative cells, **390 en** (phone emulation) and **1440 ko** (desktop), recorded at both `no-preference` and `reduce`. With four flows that's 16 short `.webm` files under `videos/<flow>/<width>-<lang>-<motion>/`.

| Flow | Real UI steps |
|---|---|
| home | clouds, Tab to the primary CTA, sky toggle, pass pause, sample tab, CTA → `/planner` |
| planner | reservation → destination (preset) → food → details → review. Tab focus on the reservation CTA and on details Next; a held press on food Next, details Next and the free-preview CTA |
| charter | Tab focus on the ICN origin; held press on Next after origin and after destination; real Next presses in between |
| tours | Tab focus ring on a catalogue card link; held press on a card; scroll the grid. The URL must still be `/tours` |

A "held press" never activates the control, so nothing advances, submits or calls the preview API. (`allowQuick` stays off, and any call would be aborted as `unknown-api`.) First the target's box has to be the same on two reads in a row (`stableBox`), and the centre is hit-tested (`hitAtCenter`, via `elementFromPoint`). Then:

- **Desktop** (`inputType: 'mouse'`): mouse down on the centre, hold 500ms, move off, release elsewhere.
- **Phone** (`inputType: 'cdp-touch'`): a CDP session from Playwright's `context.newCDPSession(page)` sends `Input.dispatchTouchEvent` `touchStart` at the centre and holds for 350ms. That's below Chromium's default 500ms long press, so no context menu. It then sends `touchCancel`, never `touchEnd`, so no tap or click is generated. The cancel and `detach()` always run in `finally`. A failed cancel is a script error. A failed detach is unverified. If the box isn't stable or the centre isn't on the control, no touch is sent and the press is `unverified`. Mouse input is never reported as touch.

The computed `transform` before and during the hold, `:active` while held, `inputType`, `stableBox` and `hitAtCenter` go into `motionProbe`. No form is submitted, and Home/product styles aren't changed or forced by the harness.

Observations aren't reported as success just because a video exists. Each of these goes into the cell's `unverified` (`motion-observation-unverified`) and makes the video state `unverified`, not `captured`:

- a Tab target that was never reached, or that was reached without `:focus-visible`
- a held press whose point missed the control, where `:active` never matched, or that wasn't sent (unstable box, CDP failure, detach failure)
- a `pointer-media-unverified` item in the cell (first activation or `videoEnd`)
- a `*Pressed` control (sky toggle, pass pause, sample tab) that wasn't rendered and so wasn't pressed

### Network contract

- Context options: `serviceWorkers: 'block'`, no storage state, downloads off. The launch uses a temporary profile.
- Routes are installed before the first navigation:
  - Exact local origin, GET/HEAD: passed through as app assets.
  - Local non-GET outside `/api`: aborted and recorded as a failure.
  - `/api/*`: only the fixtures below. Everything else is aborted and recorded as `unknown-api`, never answered with `{}`.

    | Fixture | Contract |
    |---|---|
    | `GET /api/promo-config` | `{ok:true, banner:null, popup:{enabled:false}}` |
    | `GET /api/reviews` | `{reviews:[]}` |
    | `POST /api/reviews` | only `action` `list` or `aggregate`. Response is `{reviews:[], aggregates:{}}` |
    | `GET /api/get-plan` | only synthetic planIds, never with a token |
    | `POST /api/ai-planner-quick` | only during the preview click, only for the matching preset request (above), exactly once |

  - External: everything is aborted. Recorded categories are `font`, `analytics`, `firestore-read` (expected), and `firestore-write`, `auth`, `external-write` (**failures**). Blocked external reads are listed but don't count as failures.
  - Map tiles (`basemaps.cartocdn.com`) get a local flat SVG tile, counted as `synthetic-map-tile`. These maps are **simulated**. If no tile reports loaded within 8s, the map state is `unverified` (the frame is kept).
  - WebSockets: all are closed. Non-local ones are failures.
- Second layer: proxy `http://127.0.0.1:9`. Only `127.0.0.1:<port>` bypasses it. Background networking, component updates, sync and pings are off. Any request that reaches the proxy is recorded as `escaped-route-reached-proxy`.
- This is cooperative isolation at the application level. It isn't an OS-level guarantee.

### Console and request-failure classification (no blanket filters)

- Every console `error` and `warning` is recorded, with its text, type, location URL and classification. Nothing is dropped.
- `harness-aborted-request` applies only when the line is Chromium's `Failed to load resource: net::ERR_BLOCKED_BY_CLIENT` (or `<METHOD> <url> net::ERR_BLOCKED_BY_CLIENT`) **and** the URL is one this cell's route handler actually aborted. The same text for any other URL is `unmatched-blocked-load` and fails.
- `harness-aborted-firestore` applies only to the two Firestore SDK offline lines (`Could not reach Cloud Firestore backend`, `WebChannelConnection RPC 'Listen'|'Write' stream … transport errored`), and only after this cell aborted a `firestore.googleapis.com` request. Any other Firestore text is unclassified. These patterns come from known SDK wording and haven't been checked against this build's output. If the wording differs, the lines become failures.
- Unclassified console errors are failures. Unclassified warnings are recorded but don't fail.
- A `requestfailed` the harness didn't cause is a failure, except `ERR_ABORTED`. That one is a page-initiated cancel (navigation, media, AbortController), listed under the cell's `unverified` and leaving the cell `partially-unverified`.
- Errors inside `record`/`after` hooks are failures, not footnotes. Page-settle timeouts (network idle 4s, fonts) are recorded on the state as `settle`, for information.

### Receipt and exit code

`receipt.json` holds the run meta: browser version, server kind (`vite-dev`/`built-preview`, detected from `/@vite/client`), device table, isolation notes and verdict text. Per cell it records:

- per state:
  - URL, viewport, DPR, coarse pointer, `html lang`, title, heading
  - `pointer` snapshots `beforeShot` / `afterViewport` / `afterFull` (per cell: `pointer.firstActivation`, videos also `pointer.videoEnd`)
  - `overflowX`
  - `calendarBounds` (planner date calendar only, else `null`): `clipAncestors` lists the panel and every ancestor whose computed `overflow-x`/`overflow-y` isn't `visible` (classes, rect, padding box, client/scroll width, overflow). `visibleArea` is their padding-box intersection with the viewport's X range (the page scroll isn't a clip). Month labels and the 7 weekday headers are measured by their text glyphs (DOM Range), and all day buttons and both nav buttons by their boxes. `clipped` lists any of them not wholly inside `visibleArea`, and `under44` any button whose visible part is under 44×44. `fits` is true only when both lists are empty. Otherwise the cell gets a `calendar-clipped` failure. A card or panel rect alone is not proof. Read only. `Run-Capture.ps1 -Mode planner-repair` re-captures just the 12 planner cells (360/390/430 × ko/en/ja/zh, no ffmpeg). It doesn't replace the matrix.
  - fixed/sticky layers
  - visible CTA and price boxes, with a centre hit-test (`hit`/`occludedBy`) and left/right clipping
- the SHA-256 of every file
- all console errors/warnings (classified), page errors, blocked requests, fixture hits, the quick-preview request summary (language/cityKey/days/airport prefix), failures, unverified items

Cell status is one of `captured`, `captured-with-failures` or `partially-unverified`. None of them means "looks right" or "works".

| Exit code | Meaning |
|---|---|
| 0 | Every state was captured with no recorded failure or unverified item. Still needs human review; not a functional PASS |
| 1 | Bad arguments, or a fatal launch/run error |
| 2 | Any failure, **including any screenshot or video error, or a failed `browser.close()`** (`meta.browserCloseError`, also printed). The receipt is written first |
| 3 | No failures, but some states or items are unverified |

Images in older runs aren't evidence for this one. The output dir must be new, and every file is hashed.

## Known limits (unverified unless stated otherwise)

- **Phones** are Chromium mobile emulation with the desktop UA and DPR 2. No WebKit, no real devices. Touch `:active` comes from CDP-emulated touch. It hasn't been observed in this build, and Chromium may not set `:active` before `touchCancel`. If it doesn't, the press is reported unverified.
- **Pointer flip cause** is still unknown. Items 1–3 under Pointer corrections are meant to show whether it goes away with `tap()`, or whether a screenshot causes it. Only the next actual pilot can tell.
- **Charter quote and payment framing** (`charter-quote`, `charter-payment-config-error`) assume the window is the scroll container. If it isn't, the state is `unverified`, not silently framed. Neither has been run yet.
- **Planner preview:** all four languages use synthetic fixtures. Real generation, purchase, coupons and login aren't exercised.
- **Result/map:** the plan is synthetic and the tiles are flat placeholders. The `course-route` button, PDF, translation and report submit aren't pressed.
- **Map fixture states** exist only on the dev server (`import.meta.env.DEV`). On preview they're `unverified`.
- **Tours:** Firestore is blocked, so the list is the static catalogue, the detail uses the localhost `localTourState=ready` fixture, and calendar availability is the static fallback. Realtime data isn't verified. Booking stops at a blank Step 2: Step 2 input, terms, PayPal, cart and the slot picker (this tour has no slots) aren't exercised.
- **Charter:** reaches Step 6 and the payment panel with synthetic Step 5 values. Flight lookup, address autocomplete (`place-search`), waypoints/route km, other services and vehicles, the Bus inquiry, login, the real PayPal SDK/buttons, order creation and capture aren't exercised. The Step 6 price is the app's own local computation for one fixed combination; it isn't compared with the server (`createPaypalOrder`).
- **Payment panel:** only the offline "no client ID" configuration error. This isn't evidence that payment works.
- **Account:** signed-out only. Google/phone/LINE login and signed-in pages aren't verified.
- **Cloud video:** headless Chromium may lack H.264. In that case the poster fallback is what gets recorded (see `motionProbe`). Recording needs Playwright's ffmpeg. If it's missing, video cells fail and nothing is downloaded.
- **Guard profiles** for every entry above are still pending (see the table). Until they exist, nothing in this document can be run.
- The Vitest config rejects any process-env `VITE_*` key. It relies on the guard's clean environment.
- External-route claims (OG crawler, real payments, PWA install) stay "미검증 — 운영자 확인 필요".
