# 🛠️ AI 코딩 워크플로우 — 마스터 문서

> **이 문서의 우선순위:**
> 이 문서 ≡ `antigravity-4phase.md` > `.agent/rules/*` > `.agent/workflows/*` > AI의 기본 판단
> (마스터 문서 2개 충돌 시 더 보수적인 쪽 채택)
>
> **핵심 원칙 3가지:**
> 1. 🎯 **질문 쪼개기** — 요청을 작고 구체적으로 → 정확도 ↑
> 2. 📁 **파일 나누기** — 컴포넌트별 400줄 이내 → 실수 ↓
> 3. ⚡ **병렬 작업** — 독립 파일 동시 수정 → 속도 ↑
>
> **Antigravity 작업 위임 시 추가 준수:**
> `.agent/workflows/antigravity-4phase.md` (Phase 0~4) + `.agent/workflows/anti-gravity-handoff.md` (수정 금지 영역)

## 📌 작업 시작 프로토콜

모든 새 작업 시작 전 반드시 이 순서를 따른다:

```
1. .agent/rules/ 3개 파일 읽기 (coding-rules, project-context, business-logic)
2. 이 문서 (.agent/workflows/coding-workflow.md) 읽기
3. 작업 성격에 맞는 workflow 파일 추가로 읽기:
   - 배포 → deploy.md
   - 컴포넌트 추가 → add-component.md
   - 예약 테스트 → test-booking.md
   - 실수 방지 → common-mistakes.md
   - AI 파이프라인 → parallel-departments.md
   - 품질 검수 → quality-check.md
4. 이 문서와 .agent/ 내용이 충돌하면 → 즉시 멈추고 질문
```

작업 시작 시 다음 문구로 확인:
```
"[계약서 로드됨] .agent/rules/ 및 .agent/workflows/ 읽었음. 3대 원칙 준수 시작."
```

## 🎯 원칙 1: 질문 쪼개기

### 나쁜 요청 (한 번에 너무 많이)
```
"PayPal 결제 버튼 고치고, 다국어도 추가하고, 
 공항 코드 매핑도 수정하고, UI 색상도 바꿔줘"
```
→ AI가 4가지 동시에 하다가 1~2개는 반드시 깨짐

### 좋은 요청 (하나씩 쪼개기)
```
요청 1: "PayPal 버튼 sandbox 401 에러 원인 찾아줘" → 완료 ✅
요청 2: "PayPal 버튼의 isSandbox 로직 수정해줘"   → 완료 ✅
요청 3: "공항 코드 매핑 수정해줘"                  → 완료 ✅
최종: git push (1회)
```

### 상황별 쪼개기 기준
| 상황 | 쪼개는 방법 |
|------|------------|
| 새 기능 추가 | ① 타입 정의 → ② 로직 → ③ UI 연결 → ④ 테스트 |
| 버그 수정 | ① 원인 분석 → ② 수정 → ③ 검증 |
| UI 변경 | ① 컴포넌트 → ② 스타일 → ③ 반응형 |
| 리팩토링 | ① 분리 대상 특정 → ② 새 파일 생성 → ③ import 교체 → ④ tsc |

### 만능 템플릿
```
"이 작업을 단계별로 나눠서 진행하자.
 먼저 계획을 세워서 보여줘.
 병렬 가능한 건 동시에 하고,
 각 단계마다 내가 확인할 테니까 승인 후 다음으로."
```

## ⚡ 원칙 3: 병렬 작업

### 핵심 — 파일을 나눠야 병렬이 가능
```
현재 (1개 거대 파일):
  수정A ──→ 수정B ──→ 수정C ──→ 완료     ⏱️ 3배 시간

분리 후 (독립 파일 여러 개):
  Payment.tsx ──→ 수정A ──→ ✅
  Result.tsx  ──→ 수정B ──→ ✅  ← 동시!   ⏱️ 1배 시간!
  types.ts    ──→ 수정C ──→ ✅  ← 동시!
```

### 병렬 vs 직렬 판단 기준
| 상황 | 판정 | 이유 |
|------|------|------|
| 서로 다른 컴포넌트 UI 수정 | ⚡ **병렬** | 의존 없음 |
| 독립된 API 함수 수정 | ⚡ **병렬** | 서로 안 부름 |
| 타입 정의 → 사용하는 컴포넌트 | 🔗 **직렬** | 타입 먼저 |
| 공통 훅 → 사용처 | 🔗 **직렬** | 훅 먼저 |
| 같은 파일 2곳 수정 | 🔗 **직렬** | 파일 잠금 |

> AI 파이프라인(Gemini 에이전트) 병렬 규칙은 `parallel-departments.md` 참고.

### 병렬 작업 안전 규칙
```
✅ OK:  서로 import 안 하는 파일끼리 동시 수정
✅ OK:  같은 타입을 "읽기만" 하는 파일끼리 동시 수정
❌ NO:  타입/상수 정의 + 그걸 사용하는 파일 동시 수정
❌ NO:  같은 파일을 2개 도구로 동시 수정
❌ NO:  A가 B를 import하는데 둘 다 동시 수정
```

## 🔄 작업 사이클

```
1. 요청 접수
   └─ "PayPal 수정 + UI 변경 + 다국어 추가"

2. 작업 분해 (질문 쪼개기)
   └─ ① PayPal API 수정  ② PayPal 버튼 수정  ③ UI 변경  ④ 다국어

3. 병렬/직렬 판단
   └─ ①+③+④ → ⚡ 병렬 가능 / ② → ① 끝나고 🔗 직렬

4. 대상 파일 크기 확인
   └─ 600줄 이하? → 진행 / 1000줄 초과? → 분리 먼저

5. 실행 (⚡ 병렬 배치 1 → 🔗 직렬 배치 2)

6. 매 배치 후 검증
   └─ npx tsc --noEmit → ✅ 에러 0

7. 완료 → git push 1회
```

| # | 금지 사항 | 대신 할 것 |
|---|-----------|-----------|
| 1 | 한 번에 여러 기능 요청 | 1요청 = 1기능 |

## 🚨 자가 반성 의무 (Auto-Stop Rules)

아래 중 **하나라도 발동하면 즉시 중단**하고 `workflow_report.md` 작성:

| # | 발동 조건 | 의미 |
|---|-----------|------|
| 1 | **동일 에러 2회 반복** | 근본 원인을 못 찾고 있음 |
| 2 | **같은 심볼 3회 이상 수정** | 설계가 잘못됐을 가능성 |
| 3 | **1변경 → 5개+ 파일 예상 외 파급** | 결합도 높음, 리팩토링 필요 |
| 4 | **빌드/배포 2회 이상 실패** | 접근 방식 재검토 필요 |
| 5 | **10분 이상 추측으로 진행** | 정보 부족, 사용자에게 질문 필요 |

### workflow_report.md 작성 양식

```markdown
# 🚨 워크플로우 중단 보고서

## 발동 조건
- [ ] 동일 에러 2회 반복
- [ ] 같은 심볼 3회 이상 수정
- [ ] 1변경 → 5개+ 파일 파급
- [ ] 빌드/배포 2회 이상 실패
- [ ] 10분 이상 추측 진행

## 증상
(무슨 에러/문제가 반복됐는지 구체적으로)

## 시도한 것
1. (첫 번째 시도 — 결과)
2. (두 번째 시도 — 결과)

## 실패 원인 추정
(왜 해결이 안 되는지 분석)

## 제안
- [ ] 사용자에게 확인이 필요한 항목
- [ ] 대안 접근 방식
- [ ] 필요한 추가 정보
```

**보고서 작성 후 반드시 사용자에게 보고하고 승인을 받은 후에만 계속 진행한다.**

## 🚨 Emergency Exception (상용화/프로덕션 장애)

아래 상황에서만 **3대 원칙 일부 우회 허용**:
1. 프로덕션 서비스 장애 (결제 안 됨, 페이지 크래시, PDF 백지 등)
2. 유료 사용자($9.90 결제자)에게 노출된 심각한 버그
3. 보안 이슈
4. 상용화 윈도우 데드라인 48시간 이내

### Emergency 시 허용되는 것
- 파일 크기 Lock 파일의 **surgical edit** (50줄 이내, 단일 파일 선호)
- Antigravity 4-Phase 일부 생략 (Phase 1/2 스킵 → 즉시 Phase 3/4)

### Emergency 시에도 금지되는 것
- `tsc --noEmit` 실패 상태 커밋
- Mojibake 스캔 실패 상태 커밋
- `.agent/workflows/anti-gravity-handoff.md` §절대 금지 영역 수정
- `CLAUDE.md §B` 절대 금지 규칙 위반

### Emergency 사후 48시간 내 의무
- [ ] `workflow_report.md` 작성 (원인 + 적용 diff + 재발 방지책)
- [ ] Phase 1 소급 계획서 작성 (후속 정식 작업용)
- [ ] 수정된 파일이 여전히 Lock 상태면 "분리 채무" 큐에 추가
