# Android 소유자 앱 알림 연결 보완

## 후속: 알림 인증키는 서버 안에서만 한 쌍인지 확인

- Vercel의 Secret은 저장 후 읽을 수 없다. 조회 보호를 풀거나 비밀키를 추출하지 않고, 기존 인증된 소유자 정기 작업 내부에서 공개키/개인키의 P-256 유효성과 한 쌍 여부만 불리언 세 개로 기록한다.
- 형식과 길이가 맞는 키 두 개도 서로 다른 쌍일 수 있다. 합성 키의 일치/불일치/잘못된 점과 scalar/개행과 padding을 구분해 검증한다. 진단 함수는 원문/키/파생키/해시/예외를 반환하지 않는다.
- 미인증·비활성 경로에서는 진단을 실행하지 않는다. 기존 인증 게이트/작업 반환값/기기 등록/발송 및 재시도/DB/환경변수를 변경하지 않는다. 새 시험 발송 없이 기존 정기 작업의 로그로 확인한다. 일치 판정만으로 실제 폰 수신 성공을 주장하지 않는다.

## 후속: 시험 알림의 발송 실패 원인 보존

- `SEND_REJECTED`만으로는 공급자의 인증/구독 오류, 일시적인 오류, 전송 직전 기기 검증 차단을 구분할 수 없다. 실패한 한 요청을 확인할 때 SDK 원문 대신 허용된 HTTP 숫자와 기존 outcome만 서버 로그에 남긴다. 알려지지 않은 값은 UNKNOWN/null로 제한한다.
- 시험 발송의 사전 차단은 PRE_SEND 단계와 고정 이유(DEVICE_UNAVAILABLE/DEVICE_CHANGED/ATTEMPT_TIME_INVALID)만 남긴다. 기존 반환값/장부 스키마/횟수/재시도 정책은 바꾸지 않는다. 키·응답 본문·헤더·endpoint·기기 hash·요청 ID·고객 내용을 로그에 추가하지 않는다.
- 회귀 범위는 해당 공급자 발송 함수와 단일 기기 시험 경로다. 화면/예약/메일 등 다른 기능의 추가 수동 검사는 하지 않는다. 진단 코드 반영은 실제 알림 수신 성공과 다르며, 운영의 승인된 본인 한 기기 시험 결과로 구분한다.

## 후속: 공용 cron 인증과 알림 기록 암호화 키 분리

- 공용 작업 인증키를 암호화 키로도 쓰면 목적별 설정 조건과 교체 시점이 결합된다. 승인된 전용 `OWNER_NOTIFICATION_CURSOR_SECRET`을 우선 사용하고 공용 `CRON_SECRET` 인증은 바꾸지 않는다. 전용 키가 없는 기존 배포만 이전 경로를 유지한다.
- `dedicated || legacy`는 명시된 빈 값 오류를 숨기므로 사용하지 않는다. undefined일 때만 fallback하고 최소 32바이트 검증을 유지한다. 암호 해제 실패 때 기존 키로 재시도하거나 진행 장부를 초기화하지 않는다.
- 새 키로 실행하기 전에 정확한 `owner_notification_control/v1`의 존재 여부를 확인한다. 기존 장부가 있으면 삭제/초기화 없이 별도 이관한다. 신규 시작은 기존 첫 실행 계약에 따라 현재 시점부터이며 과거 고객 자료를 소급 발송하지 않는다.
- 전용 키 우선순위/명시 오류 차단/기존 호환/암호화 왕복/공용키 변경 영향 분리/잘못된 키 거절을 가짜 값 회귀로 검증한다. 실제 키 값이나 운영 비밀 설정의 구체적인 실패 원인은 공개 기록에 넣지 않는다.

## 실수와 재발 방지

- TWA 실행과 웹 Push 지원만으로 Android 앱 알림이 연결됐다고 판단하지 않는다. 기존 1.0.1에는 POST_NOTIFICATIONS, ABH DelegationService, NotificationPermissionRequestActivity가 모두 없었다.

- ABH 공식 알림 샘플과 실제 사용하는 2.7.3 AAR의 세 클래스를 확인하고 기존 인증·주소·서명은 유지한다. 알림 권한 외 연락처·사진·위치 등은 추가하지 않는다. 권한은 사용자 동작에 따라 요청하며 강제 승인하지 않는다.
- 소스 문자열뿐 아니라 최종 APK를 aapt2로 읽어 권한, 비공개 권한 요청 Activity, 검증된 브라우저만 받는 ABH 서비스와 정확한 intent-filter를 검사한다. 누락·중복·잘못된 소속·공개 Activity·권한 SDK 상한을 거부한다.
