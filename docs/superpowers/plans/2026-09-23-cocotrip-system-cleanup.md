# CocoTrip 시스템 정리 계획표

> 실행 담당: 승인된 작업은 `superpowers:executing-plans`에 따라 단계별로 진행한다. 계획·위험 판단·최종 검수는 Astra, 범위가 정해진 비민감 구현·검사는 사용 가능한 가벼운 모델이 맡는다. 이 문서는 정리 순서와 완료 기준이며, 아직 재현하지 않은 문제의 수정 지시가 아니다.

**목표:** 고객이 시작한 작업이 결과까지 이어지고, 문제가 생긴 단계와 수정 영향을 확인할 수 있도록 기존 시스템을 정리한다.

**접근:** 고객 흐름별 연결 검사를 먼저 확보한다. 그 근거로 중복 요청·중복 계산·낡은 분기를 줄이고, 같은 결과를 화면·저장·PDF·공유가 일관되게 사용하도록 정리한다. 기존 저장 형식과 보호 규칙은 보존한다.

**기술 구성:** React/Vite, 서버 API, Firebase/Firestore, Gemini, 기존 Vitest·Playwright. 새 의존성·별도 관리 시스템 도입은 현재 계획에 없다.

**근거:** [현재 플래너 점검 결과](../../PLANNER-JOURNEY-CHECKLIST-2026-09-23.md), 기존 91개 기능 점검 항목과 개선 8개, 이번에 재확인한 `src/App.tsx`, `api/_ai_core/handlerCore.js`, `package.json`, 기존 검사 명령. 전체 프로젝트 재감사를 이번 계획 작성에서 수행한 것은 아니다.

## 현재 위치

- 기능 목록: 고객 38개, 관리자 28개, MOOD 16개, 웹·Brain·Python 연결 9개 = **91개 점검 항목**. 91개 정상 판정이 아니다.
- 플래너 무료 미리보기 중복 요청 수정은 **로컬 검증 완료·미커밋·미배포**다. 기존 제품 1개·테스트 3개·문서 2개 변경을 보존한다.
- 미리보기, 저장 함수, PDF, 공유를 각각 실행한 근거가 있다. 같은 일정의 전체 생성→저장→조회→PDF/공유 연결은 아직 미확인이다.
- 기존 `plan:test`는 생성 후 후처리를 검사하며 저장을 생략한다. 기존 테스트 수나 배포 성공만으로 고객 흐름 완료를 판정할 수 없다.
- 기존 개선 번호를 유지한다: FIX-01 생성 중단, FIX-02 다양성, CHECK-03 전체 흐름, CHECK-04 외부 전달, FIX-05 속도, TEST-06 검사 구성, TEST-07 타입 검사 착시, OPS-08 오류 추적.

## 검사·비용 운영

- 수정 중에는 해당 흐름의 실행 검사와 변경 파일 린트를 우선한다. 같은 내용을 확인하는 테스트를 개수 목표로 추가하지 않는다.
- 기존 `npm run plan:test -- sample`은 후처리 근거로 사용한다. 전체 생성·저장 검사로 집계하지 않는다.
- `npm run build`가 실제 타입 검사다. `tsc --noEmit`이나 현재 `verify:all`의 초록 결과를 타입 통과 근거로 쓰지 않는다.
- 현재 푸시 훅의 빌드·전체 단위검사·크기·오답 패턴·React 훅 검사는 유지한다. 변경 없는 전체 검사 수동 반복과 여러 차례 푸시를 줄인다. 게이트 변경은 별도 검토한다.
- 결함은 `재현 입력 / 실패 단계 / 영향 / 최소 수정 / 회귀 근거 / 로컬 상태 / 운영 상태`로 기록한다. 단순 파일 분할 개수·테스트 개수·전체 완료율을 성과 목표로 삼지 않는다.
- Gemini 실제 호출은 승인된 횟수와 비용 상한 안에서만 한다. 평소에는 공개 합성 자료와 외부 경계 대체를 사용한다. API 비용 절감 수치는 동일 조건의 호출 기록을 얻은 뒤 보고한다.
- 현재 계획 수행에 새 유료 서비스·플러그인은 필요하다고 판단할 근거가 없다. 기존 GitHub, 오류 수집, 테스트 장치와 점검 스킬을 먼저 쓴다.

## 담당·범위·출시

- **Astra:** 순서 결정, 연결 구조·돈·권한·식이 위험 판단, 변경 승인 범위 확인, 최종 검수.
- **가벼운 모델:** Spark 접근 가능 여부에 따라 우선 검토하고, 사용할 수 없으면 Luna 등 가용 모델로 범위가 정해진 구현·문구·검사를 수행한다. 실제 모델과 맡긴 일을 기록한다. 이번 문서는 계획 작성이며 새 구현 위임을 실행한 것은 아니다.
- **병렬 수:** 기본 한 흐름씩 진행한다. 파일 소유권과 검사 대상이 겹치지 않는 경우에만 가벼운 작업 2개까지 병행한다.
- **보호 경계:** 결제·환불·가격·할인·예약 처리·권한·개인정보·식이 보호 변경, 운영 DB 접근, 유료 API, 실제 발송·게시·결제·배포는 기존 승인 범위를 확인한다. 해당 승인 없이 보호 규칙을 완화하거나 실행하지 않는다. 안전한 분리 검사는 계속한다.
- **출시 단위:** 재현→최소 수정→관련 검사/린트→최종 빌드와 필수 훅→브랜치 PR→해당 변경의 승인된 머지/배포→대상 버전 확인→기록. 실패하면 이전 배포로 되돌릴 수 있는지와 데이터 변경 유무를 먼저 확인한다.
- **범위 제한:** 계획 밖 신규 기능, 일괄 재작성, 일괄 삭제, 무관한 의존성 교체, 테스트 보호 약화는 포함하지 않는다.
- **문서 위치:** 저장소에서 관리한다. 바탕화면에는 새 보고서를 만들지 않는다.
- **일정:** 우선 0·1을 한 작업 묶음으로 완료한다. 이후 2·3, 4·5, 6·7 순서로 묶되 비용 위험이나 고객 진행 불가가 확인되면 앞당긴다. 달력 일정은 첫 연결 검사에서 실제 막힌 지점과 승인 대기 시간을 확인한 뒤 정한다.

## 정리 완료의 의미

91개 관리 항목의 담당 경로·검사 근거·남은 조건을 찾을 수 있고, 핵심 고객 흐름은 처음부터 끝까지 실행된다. 발견된 중대한 결함과 운영 미확인 항목이 숨지 않으며, 변경 후 필요한 검사와 비용을 예측할 수 있어야 한다. 알려진 중대한 결함이 남아 있으면 전체 안정화 완료라고 보고하지 않는다.

이 계획표 작성만으로 제품 정리가 완료된 것은 아니다. 이번 계획 작성에서 제품 코드·기존 테스트·바탕화면 파일·배포 상태를 변경하지 않았다.
