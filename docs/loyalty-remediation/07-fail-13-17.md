# 07 — 머지 전 보완 (FAIL-13 ~ FAIL-17)

시점: 2026-07-29 · 개인정보 없음
**이 라운드의 운영 Firestore 쓰기는 0건이다.** 보정 재실행 없음 · rollback 실행 없음 · 머지 없음.

## FAIL-13 (P0) — 계정 전환 시 이전 계정 개인정보 잔상

`useLoyalty` 는 회원 문서 하나만 `loadedUid` 로 추적했다. 그래서:

| 상황 | 예전 결과 |
|---|---|
| A 전부 로드 → B 회원 문서만 도착 | ready 가 켜져 **A 의 쿠폰·적립 이력이 B 화면에 노출** |
| B 회원 문서가 없음 | `setLoyalty` 자체가 호출되지 않아 **A 의 등급·코인이 남음** |
| 구독 오류 | 이전 계정 값이 그대로 남음 |

값과 uid 를 한 덩어리(`{ uid, value }`)로 묶고, **세 갈래가 전부 현재 uid 것일 때만** 노출한다.
"누구 것인지 모르는 값" 이 존재할 수 없는 구조다.

- 회원 문서가 없으면 `{ uid, value: null }` 로 **명시 기록** — 이전 값이 남을 자리가 없다
- 구독 오류도 현재 uid 의 빈 값으로 확정 — 이전 계정 자료로 대체되지 않는다
- 구독 해제 뒤 늦게 도착한 A 콜백은 `cancelled` 가드로 버린다(B 가 다시 로딩으로 되돌아가지 않게)
- Bronze·0 깜빡임 방지와 회수 쿠폰(`isRevoked`) 필터는 그대로 유지

회귀 잠금: `tests/unit/use-loyalty-account-switch-leak.test.tsx` — 도착 순서 6가지 전부,
로그아웃 경유, 구독 오류, 늦은 콜백, 회수 쿠폰 미노출.

## FAIL-14 — rollback dry-run 이 허수 검사였다

스냅샷 문서만 읽어 "복구 예정" 이라 찍었다. 현재 사용자·correction·쿠폰을 아무것도 확인하지 않았다.

dry-run 과 execute 가 **같은 함수**를 쓰게 했다.

```
readAndEvaluate(read, userRef, snapshotData, planHash)
  → evaluateRollbackTarget(...)   ← 판정은 여기 한 곳뿐
```

dry-run 은 `read = (ref) => ref.get()`, execute 는 `read = (ref) => tx.get(ref)` 를 넘긴다.
판정이 두 벌이 될 수 없으므로 dry-run 이 `ready` 라고 한 계정만 execute 에서도 통과한다.

- 계정별로 `ready` / `stale_rollback` / `plan_mismatch` / `correction_missing` /
  `already_rolled_back` / `coupon_drift` / `correction_invalid` 를 실제 판정한다
- "복구 가능" 은 **모든 검증을 통과한 계정에만** 표시한다
- 복구 불가 계정과 사유를 익명 순번으로 보고한다
- dry-run 쓰기 0건은 `guardFirestore(allowWrites: false)` 로 **코드가 막는다**

## FAIL-15 — rollback 의 correction·쿠폰 검증이 불완전했다

correction 은 존재 여부와 `rolledBack` 만 봤다. 쿠폰은 셋만 봤다.

이제 rollback 도 `identifyPollutionCorrection()` 을 반드시 호출한다(FAIL-8 과 같은 기준).
추가로 되돌릴 목표값인 `balance` · `tierAfter` 가 유효한지 확인한다 — 없으면 추측으로 채우지 않고 중단.

쿠폰은 회수 필드 **전부**를 확인한다.

| 필드 | 기대값 | 어긋나면 |
|---|---|---|
| `isRevoked` | `true` | `already_unrevoked` |
| `status` | `revoked` | `status_changed` |
| `revokedReason` | `issued_from_unverified_ai_plan_coins` | `reason_changed` |
| `revokedPlan` | 이 planHash | `revoked_plan_changed` |
| `revokedAt` | 존재 | `revoked_at_missing` |
| `isUsed` | `true` 아님 | `used_after_revoke` |

하나라도 어긋나면 **그 사용자 rollback 전체를 중단**한다(부분 복원 금지).

필드 목록·회수 사유·문서 ID 규칙은 core 한 곳에만 둔다. 실행부와 rollback 이 서로 다른 정의를 보면
"썼는데 못 되돌리는" 필드가 생긴다.

## FAIL-16 — 인정 안 된 correction 계정은 자동 보정 금지

예전에는 `ambiguousCorrections` 를 **보고만 하고** 자동 보정 대상에는 넣을 수 있었다.
그 correction 이 이미 무엇을 뺐는지 모르므로, 현재값에서 오염분을 다시 빼면 두 번 차감할 수 있다.

- 인정되지 않은 correction 이 **하나라도** 있으면 그 계정은 `manual_review` 로 분리
- `changed = false` → 실행 대상과 planHash 에서 자동 제외
- 실행 모드에서 절대 쓰지 않는다(`docsToWrite = 0`)
- 보고서에는 **예상 영향만** 표시하고 운영자 판단으로 남긴다

`rolledBack` 인 correction 도 같은 경로다 — "이미 제거된 몫" 으로 세지 않아 오염이 다시 보이지만,
자동으로 빼지도 않는다.

## FAIL-17 — 감사 합계와 익명 계정 연결

### 합계를 두 범위로 나눈다

모든 합계가 `changed` 계정만 더했다. 보정이 끝나 대상이 0 이 되면
"오염 이력 0건 / 인정 correction 0건 / 지출 $0" 처럼 찍혔다. 실제로는 오염 이력 209건이
그대로 남아 있고 인정 correction 도 4건 있다.

| 범위 | 담는 것 |
|---|---|
| `totals.allScanned` | 현재 전체 지출·예약·코인, 역사적 오염, 인정 correction 과 이미 제거된 몫, **남은 미보정 오염**, ambiguous 수, manual_review 계정 수 |
| `totals.plannedTargets` | 실행 대상 계정 수, 전후 값과 차이, 실행 시 문서 수 |

용어도 바꿨다 — "오염 이력 0건" 금지, "역사적 오염 이력 209건 / 남은 미보정 오염 0건" 으로 쓴다.
대상이 0 건이어도 현재 전체 합계 $47,996.81 / 59 / 140,642 가 그대로 나온다.

### 익명 순번을 안정화

예전에는 보정 대상만 순번을 매겨, 대상이 줄면 번호가 통째로 밀렸다(같은 사람이 문서마다 다른 번호).

정렬 기준을 **보정으로 바뀌지 않는 값**으로 바꿨다: 오염 코인 → 오염 금액 → 오염 건수 → uid(동점 처리).
오염 이력은 삭제하지 않으므로 이 값은 보정 전후로 같다.

- 실행부 로그도 보고서와 같은 번호를 쓴다
- 복구 스냅샷에 `accountNo` 를 남겨 rollback 도 같은 번호를 이어 쓴다
- 문서상 $253,204.54 계정은 사후에도 **user-1** 이다
- 옛 스냅샷에는 `accountNo` 가 없어 순서로 대체한다
