# Control Tower 받은함 보관 운영 설명서 (2026-09-09)

## 결론

승인된 범위는 다음 세 가지다.

- 일반 문의 사본과 그 문의에 묶인 확인 가능한 답장 사본은 **상담을 일반 종료한 뒤 30일**까지만 둔다.
- 실제로 보내지 않은 답장 초안은 최대 **7일**만 둔다.
- 진행 중 상담과 법정 증빙·분쟁 검토가 필요한 건은 자동 삭제 대상이 아니다.

현재 회사 Gmail·WhatsApp 수신은 기본 OFF이며, 실제 계정 연결·수신·삭제를 확인한 상태가 아니다. **이번 작업에서 실제 고객 데이터 삭제는 실행하지 않았다.** 기존 DB의 전체 삭제 이력을 조회해 0건으로 확인했다는 뜻은 아니다. 이 문서는 법정 자료 보존 시스템이 완성됐다는 선언이 아니라, 일반 문의 사본의 제한된 자동 정리 계약이다.

## 시간 기준 두 가지

두 30일은 다른 기준이다.

| 기준 | 적용 대상 | 뜻 |
|---|---|---|
| 수신 나이 최대 30일 | 새 Gmail·WhatsApp 수신 | 공급자에서 늦게 도착한 오래된 원문을 새 v2 사본으로 다시 넣지 않는다. 기존 `*_RETENTION_DAYS`보다 길게 허용하지 않는다. |
| 상담 종료 뒤 30일 | 일반 상담 사본 | 운영자가 `ordinary_no_evidence` 확인으로 상담을 닫은 시점부터 계산한다. 이 시점이 와야 사본 정리가 가능하다. |

새 v2 문의 사본은 `expiresAtMs: 0`, `expiresAt: null`로 저장한다. 수신 시각만으로 TTL 삭제를 약속하지 않으며, 상담 단위 상태와 실제 삭제 작업이 결정한다. 기존 `COMPANY_GMAIL_INBOX_RETENTION_DAYS`와 `WHATSAPP_INBOX_RETENTION_DAYS`는 **기존 형식 호환과 새 수신의 시작·신선도 제한**용이다. 상담 종료 뒤 30일 정책을 환경변수 값으로 늘리거나 줄이지 않는다.

기존 legacy 사본은 자동으로 v2로 이관하지 않는다. legacy 읽기·보관 규칙은 그대로 두며, 형식이 불명확한 문서를 넓게 삭제하지 않는다.

## 무엇을 지우고 무엇을 남기는가

일반 종료된 case가 30일을 넘고, 실제 삭제 시점에도 case가 여전히 일반 종료 상태일 때만 해당 case의 v2 문의 사본과 그 원본 문의에 정확히 묶인 답장 장부를 같은 거래 안에서 지운다. 마지막 사본까지 정리된 만료 case 메타도 남기지 않는다.

다음은 자동 삭제하지 않는다.

- open(진행 중) case와 protected(증빙 보호) case
- 재개된 상담에서 새로 들어온 본문. 이전 만료 구간(`expiredThroughMs`) 이하의 오래된 사본만 정리한다.
- legacy, 다른 계정·다른 case, 오염·형식 불명 문서
- `sending`, `outcome_unknown` 또는 상담 종료 뒤 변경된 답장 장부
- 7일이 지났더라도 이미 공급자가 받은 전송 이력. 이는 미발송 초안이 아니다.
- Gmail/WhatsApp 공급자 원본, 예약·결제·환불·고객 DB, 다른 전송 장부

초안 7일 정리는 `draft`·`draft_only`·아직 시도하지 않은 `approved`만 대상이다. 해당 회사의 v2 원본 문의·상담을 같은 거래에서 확인하며 증빙 보호 초안은 남긴다. 원본이나 소속을 확인하지 못하면 삭제하지 않고 확인 필요로 표시한다. 확인 가능한 `provider_accepted` 답장 사본은 전역 정리로 독립 삭제하지 않고, 위 일반 상담 사본 정리에서만 원본 문의와 함께 처리한다.

## 실행과 안전 장치

Vercel cron은 매시 **23분**에 `external-inbox-retention-sweep`을 호출한다. Production이 아니거나 수신 채널이 하나도 준비되지 않으면 DB를 시작하지 않고 정리도 하지 않는다. 새 키·권한 변경은 필요 없다.

만료 시 조회를 막는 것과 실제 파일·문서를 지우는 작업은 다르다. 실제 삭제는 다음 정기 실행에서 제한된 건수로 처리하며, 오류·미완료 페이지·증빙 검토가 있으면 더 늦어질 수 있다. 정확히 만료 시각에 물리 삭제되거나 항상 한 시간 안에 끝난다고 보장하지 않는다. AI를 호출하지 않지만 서버·DB 사용료까지 0원이라는 뜻은 아니다.

작업은 로그에 고객 본문·공급자 응답·오류 내용을 쓰지 않는다. 삭제 전후에는 실제 시각을 다시 읽고, case revision과 상태를 거래 안에서 다시 확인한다. 스캔 뒤 상담이 재개되거나 증빙 보호로 바뀌면 삭제 대신 검토 필요 상태로 멈춘다. 정리 오류나 시간 이상을 성공으로 표시하지 않는다.

관리자 받은함은 `retentionMaintenance` 요약만 보여 준다.

| 상태 | 의미 |
|---|---|
| `not_active` | 준비된 수신 채널이 없어 정리 조회도 하지 않음 |
| `ok` | 성공 기록이 2시간 안에 있음 |
| `delayed` | 마지막 성공 기록이 2시간을 넘음 |
| `attention` | 정리 작업이 실패했거나 운영자 검토가 필요함 |
| `unknown` | 기록이 없거나 오염되었거나 읽지 못함 |

이 요약은 마지막 실행에서 확인한 정리 수량이며 전체 누적 수량이 아니다. 늦게 도착한 UI 응답이 현재 정리 상태를 증명한다는 뜻도 아니다. 내부 오류 코드·오류 원문·고객 본문은 이 요약 응답에 노출하지 않는다.

## 색인과 배포

미발송 초안 정리는 `external_inbox_reply_workflows`의 `status ASC, createdAtMs ASC` 복합 색인이 필요하다. 이 색인은 `firestore.indexes.json`에 선언되어 있다. 이 파일이 main에 반영되면 GitHub Actions의 **Deploy Firestore Indexes**가 추가 전용 REST 배포와 완료 대기를 수행한다.

색인 생성은 백필 때문에 시간이 걸릴 수 있다. Actions 성공 뒤에도 운영자는 Firestore Console의 Composite Index 상태가 READY인지 확인한다. 새 GitHub Secret, Vercel 환경변수, 권한 변경은 이 작업에 추가하지 않는다.

## 법정 자료와 구분

30일/7일은 승인된 운영 기준이지 모든 기록에 적용되는 법정 보존기간이 아니다. 보유 목적이 사라진 개인정보의 파기와 법령상 보존자료의 분리 보관은 [개인정보 보호법 제21조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1027063705), 계약·대금·분쟁 관련 기간은 [전자상거래법 시행령 제6조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1018638379)를 기준으로 구분한다. 증빙 보호 버튼은 삭제 보류일 뿐, 별도 법정 기록 보관 체계나 적법성 검토를 대신하지 않는다.
