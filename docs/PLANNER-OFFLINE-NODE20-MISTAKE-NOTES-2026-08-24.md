# 플래너 오프라인 하네스 — Node 20 호환 오답노트 (2026-08-24)

## 무엇이 실패했나

- 로컬 플래너 하네스가 `node:module`의 `registerHooks`를 가져왔다.
- 로컬 Node 22.15에서는 동작하지만, 필수 GitHub `unit` 검사는 Node 20.20.2를 쓴다.
- 새 저장 전 품질 테스트가 이 오래된 불일치를 처음으로 CI에서 실제 실행했다.

## 근본 원인

로컬 성공은 개발 PC의 실행 환경만 증명했다. 저장소가 정한 CI 실행 환경까지 증명하지 못했다. 모든 저장소 검사가 Node 20을 기준으로 하는데 하네스만 Node 22.15 이상 전용 기능에 의존했다.

## 재발 방지

- Node 20.6부터 지원하는 `module.register`를 사용하고, Firestore·교통·Axios 경계만 로컬 파일로 돌린다.
- 바뀌는 fixture 상태는 loader thread가 아니라 실제 앱이 도는 영역에 둔다.
- 출시 전에는 CI와 정확히 같은 실행 환경으로 하네스를 돌린다.

```bash
npx -y node@20.20.2 scripts/plan-local/run.mjs sample
npx -y node@20.20.2 node_modules/vitest/vitest.mjs run tests/unit/plan-local-prewrite-quality-gate.test.ts
```

- 특정 Node 버전 기능을 쓰면 개발 PC 기본 Node의 통과만으로 완료 처리하지 않는다.

## 2026-09-23 — 중복 차단 통과와 일정 생성 성공을 구분

- 최종 중복 게이트 테스트가 통과해도, Gemini가 같은 코스를 두 번 선택하면 실제 생성은 422로 종료된다. 기존 부산 남포 코스를 반복 선택하는 입력으로 자갈치시장 중복을 오프라인 재현했다. 당시 운영 실패의 원본 선택 결과는 없어 동일 원인이라고 확정하지 않는다.
- 단도시 정상·누락 응답과 다도시 선택에서 반복된 일반 코스만 같은 도시의 미선택 일반 코스로 보정한다. 나중 날의 정상 선택·활동 코스·식이 검증·최종 중복 차단은 보존하고 Gemini 재호출은 추가하지 않는다. 대안이 없거나 서로 다른 코스의 장소가 겹치면 기존 검사가 계속 차단한다.
- 회귀 검사는 SDK 경계만 대체하고 실제 선택 → 일정 확장 → 최종 중복 판정을 연결한다. 잘못된 ID를 포함한 짧은 응답, 캐시 사용량 보존, 활동 코스를 새로 끼워 넣지 않는 것도 확인한다.
- 일정 간 다양성 실패는 별도 문제다. 고정 비교쌍의 7/13 겹침에서 공통 숙소 하나만 빼도 6/12=50%이며 기준 미달이다. 원본 두 일정 없이 원인을 추측해 수정하거나 기준 30%를 완화하지 않는다.

## 2026-09-23 — admin bypass만으로 실제 planner 경로를 단정하지 않기

- `ADMIN-BYPASS-`는 Gemini `plannerMode`를 legacy로 고정하지만 handler는 먼저 block-mode를 시도한다. 실행 진단은 성공 응답 `_debug`의 `blockModeUsed`를 우선하고, 전체 debug/응답 대신 허용 목록과 형식 검사를 통과한 코스 ID만 기록한다.

## 2026-09-23 — 최근 일정 회피 정보는 실제 선택 경로까지 전달해야 함

- 최근 3개 일정의 식당 정보가 legacy 프롬프트에만 들어가 block-mode에서는 사라졌다. 기존 사용자 범위 조회를 한 번만 사용해 식당명과 코스 ID를 전달한다. 수정 요청은 새 회피 대상에서 제외한다.
- 과거 식당과 현재 일정의 사용 식당은 별도로 관리한다. 과거 후보가 소진돼도 현재 일정 안의 미사용 식당을 먼저 고른다. 앵커가 있으면 기존 1순위보다 멀어지는 대안은 채택하지 않고 식이 신뢰 필터를 그대로 유지한다.
- 최근 코스 ID는 조건에 맞는 대안 선택을 돕는 참고 정보다. 코스를 강제로 바꾸거나 추가 Gemini 호출을 하지 않는다. 이력 없음·대안 부족·같은 코스 응답은 전체 다양성 목표를 보장하지 않는다.
- SDK 응답을 고정한 합성 자료에서 같은 코스는 100%, 다른 코스도 식당 수렴으로 33.33% 겹침을 재현했다. 회피 지시를 따르도록 mock을 만들거나 이 결과를 실모델 성공으로 보고하지 않는다. 운영 30% 미만 기준은 유지한다.
- scratch 검사는 설정 병합으로 기존 전체 include가 합쳐질 수 있다. 실행 파일 경로도 명시해 불필요한 전체 검사를 막는다.
- handler 줄 수 제한은 끝의 줄바꿈까지 세는 기존 테스트 기준으로 확인한다. 커밋 훅의 물리적 줄 수 통과만으로 전체 검사의 500줄 제한 통과를 단정하지 않는다.
- 오류 시 빈 문자열을 반환하던 함수를 구조화 결과로 바꾸면 정적 오답 검사도 함께 확인한다. 반환 형태만 보지 말고 빈 결과와 알림을 유지하는지 실행 검사로 확인하고, 빈 결과가 사라지는 회귀도 차단한다.

## 2026-09-23 — 실모델 선택 2회 로컬 검증

- 공개 서울 코스 24개와 식당 1,866개로 만든 로컬 fixture에서 같은 서울 2일·Meat·한국어 조건으로 2회 생성했다. 첫 실행은 이력 없이, 두 번째는 첫 결과의 최근 식당·코스 정보를 전달했다.
- 실제 선택은 Jongno/Hongdae에서 Yongsan/Mangwon Local로 달라졌고 코드 후처리에서도 선택은 유지됐다. 전체 겹침은 1/11=9.09%(망원시장), 식당은 0/6 겹쳤으며 양쪽 중복 게이트가 통과했다.
- 실제 SDK·fetch mock은 없었고 운영 DB 조회·저장·발송도 없었다. 최근 이력은 메모리 fakeDB에서 이어 붙였다. 이 두 번의 관측은 특정 입력의 결과이며 장기간 다양성이나 모든 입력의 성공을 보장하지 않는다.
- 요청은 모두 HTTP 200. 기록 토큰은 입력 4,772+4,794, 후보 151+163, 생각 852+1,434로 합계 12,166이다. [Google 공식 표준 단가](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash)로 계산한 약 $0.037749는 추정치이며 실제 청구액 확인값이 아니다.
