# AI 운영센터 오답노트 — 2026-08-31

- PWA 등록은 렌더 중 시작되고 보호 훅의 mount는 이후 effect다. 첫 mount 이전 완료 신호를 버리면 이미 활성화된 업데이트가 계속 시간 초과될 수 있다. 첫 mount 전 준비 상태만 보존하고, 실제 해제 뒤 늦은 콜백은 계속 무시하는 두 경우를 나눠 검사한다.
- 서비스워커 활성화 요청 전 검사를 통과해도 실제 controlling 콜백 때는 입력/결제 상태가 달라질 수 있다. 새로고침 경로를 하나로 모으고 직전 상태·요청 시각·조작 순서를 다시 확인한다. 설치된 등록 라이브러리 원본을 실행해 다른 창 업데이트의 기본 강제 리로드도 회귀로 잠근다.
- 조회 원본 하나의 연결 누락이 전체 예약 작업을 매번 멈추면 정상 문의까지 영구 누락된다. 모호한 원본은 발송/건너뛰기 없이 해당 소스만 보류하고, 독립 원본과 이미 대기한 발송은 계속하는지 반복 실행으로 검사한다.
- 정확한 이어 읽기에는 같은 시각의 문서 ID까지 필요하다. 원본 ID를 전송 장부에 평문 복사하지 말고 별도 암호화 제어 상태로 보존한다. 키/기기/설정 변경·변조 때 자동 재초기화하면 과거 발송이나 누락이 생기므로 보류한다. OFF일 때 DB 0회면 보관기간 정리도 실행되지 않는다.
- 보호된 Preview 검사에서 PR 코드에 비밀값을 맡기지 않는다. 신뢰한 main의 도구와 고정 도구 버전, 같은 저장소/정확한 SHA/배포 호스트를 검증한다. main에 새 도구가 아직 없는 첫 PR은 승인된 머지 후 같은 Preview를 다시 검사하며, 인증 전 실패를 앱 점수 통과로 표시하지 않는다.
- React 렌더 중 ref.current를 읽어 설치 여부 prop으로 넘기면 현재 린트가 거부한다. 고정 초기값은 useState 초기화로 보존하고 최신 입력/결제 상태는 콜백 시점에 DOM에서 확인한다.
- 같은 자동화 원본이 상태 카드와 긴급 업무 목록에 따로 표시된다. 한곳만 이름을 고치면 다른 곳의 오해가 남는다. 실제 원본 식별값과 제목 형식을 확인해 표시만 맞추고 서버 수량·다음 행동·링크·다른 원본의 같은 문구는 보존한다.
- Lighthouse 작업이 성공이어도 실제 검사 URL이 Vercel 로그인 페이지일 수 있다. 인증 배선, 최종 URL, 원본 보고서 수, 실행 오류와 필수 assertion을 따로 확인하고 continue-on-error로 숨겨진 오류를 통과로 세지 않는다. assertion-results.json은 정상 전부 통과 시 빈 배열일 수 있으므로 파일 없음과 구분한다.
- email_retry는 받은편지함이 아니라 pending_email_retries 발신 재시도다. 상태 카드 제목만 보고 수신 문의 연결로 확대하지 않는다. API 비용 역시 기록된 Gemini 추정 사용액과 전체 업체 실제 청구액을 구분한다.
- 서비스워커 알림 클릭에서 첫 기존 창을 이동시키면 운영 알림이 작성/결제 화면을 덮을 수 있다. 새 업무 푸시를 연결하기 전에 대상 창 선택과 기존 작업 보호를 별도로 검사한다.
- 성공한 자료가 남아 있어도 다음 갱신 실패는 숨기지 않는다. `error && !data`는 오래된 예약을 '갱신 완료'로 오인시킨다. 첫 실패뿐 아니라 성공→실패→재시도 성공을 화면/시각/기존 행 보존까지 검사한다.
- 목록을 `slice(0, 10)` 또는 `slice(0, 30)`으로 줄일 때 더보기 없는 총 개수 배지는 업무 누락을 만든다. 마지막 묶음까지 열고, 표시 수/전체 수와 마지막 버튼 초점을 검사한다. 서버 원본 조회 한도와 화면 더보기는 별개다.
- 목록 기간은 화면 내부 state에만 두면 원본 링크에서 돌아올 때 초기화된다. URL에 기간만 저장하고 기존 쿼리/해시를 보존하며 replace로 변경한다. 고객 식별자나 업무 내용을 URL에 추가하지 않는다.
- '7일' 이름과 실제 +8일 계산을 혼동하지 않는다. 이 화면의 기존 서버 범위는 오늘 + 향후 7일이다. 표시만 명확히 하고 서버 집계/결제/예약 상태는 바꾸지 않는다. 한국 자정·마지막 포함일·제외일을 검사한다.
- 1280px 화면만 확인하면 1024px 두열 시작점에서 카드 내부 고정 4열이 겹치는 결함을 놓친다. 예약 카드의 이름/날짜는 두 칸, 상태는 다음 줄로 유지하고 실제 간격을 확인한다. 모바일 바깥 그리드에는 명시적 한 열과 최소 너비 0을 사용해 긴 영어의 가로 넘침을 막는다.
- 고정된 8월 31일 미리보기는 날짜가 지나면 오늘 예약은 빈 목록인데 요약만 남는 허수 검증을 만든다. 현재 한국 날짜의 가짜 행에서 요약도 계산하고 긴 목록/빈 상태/부분 실패/갱신 실패를 분리한다. 정적 실패 화면은 실제 통신 실패→재시도 시험의 대체가 아니다.
- 설치 프롬프트는 한 번만 사용할 수 있다. 클릭 직전 잠금과 공유 포인터 제거, 취소/예외 복구, unmount 후 상태 갱신 방지를 검사한다. accepted와 standalone은 APK 설치 완료나 업무 알림 실수신의 증거가 아니다.
- APK 빌드·서명·설치 `Success`·OS 실행 요청 `Status ok`는 실제 화면 성공을 뜻하지 않는다. ABH 2.7.3은 시작 중 `ManageDataLauncherActivity`를 참조하므로 비공개 등록과 고정 주소를 소스와 최종 병합 Manifest에서 각각 검사하고, 새 실행의 프로세스 오류·재진입·화면을 따로 확인한다. 이전 실행의 충돌 로그를 새 버전 오류로 재사용하지 않는다.
- 새 Android worktree에는 무시된 `local.properties`와 서명키 연결이 따라오지 않는다. 기존 보호 키에 연결한 로컬 설정과 Git 제외 상태를 먼저 확인하고 보호 실행기로 빌드한다. 설정 누락 때문에 키를 새로 만들거나 암호를 파일에 기록하지 않는다.
- `findByRole('status')`는 성공 DOM이 생긴 것만 기다리며, 이후 useEffect의 초점 이동 완료까지 보장하지 않는다. 키보드 접근성 검사는 초점 대상이 실제로 바뀔 때까지 `waitFor`로 확인한다. 기다림 없이 즉시 비교하면 전체 병렬 실행에서 간헐적으로 실패한다.
- Windows checkout의 CRLF와 apply_patch의 LF가 섞이면 정확한 문자열 치환으로 만든 회귀검사가 실제로 코드를 바꾸지 못할 수 있다. 테스트 입력은 LF로 정규화하되 운영 배포 후보의 원문 보존은 LF/CRLF 각각 바이트 단위로 검사한다.
- Firestore 규칙은 Vercel 웹 배포와 별개다. 승인된 일부 조건을 고칠 때 운영과 저장소 전체 규칙의 기존 차이를 먼저 확인하고, 관련 없는 차이를 함께 배포하지 않는다. 현재 운영 원문에 승인된 조건만 더한 후보를 검사하고 배포 직전 기존 ruleset·해시가 달라졌으면 중단한다.
- Firestore 조회 성공을 가짜 함수로만 검사하면 실제 보안 규칙 오류를 놓친다. `request.resource`는 쓰기 요청에만 있으므로 읽기 허용 조건에서 참조하면 본인 문서도 거부될 수 있다. 운영 규칙을 읽기 전용으로 대조하고 가상 요청으로 재현한 뒤, 보안 변경은 별도 승인받는다.
- 알림 권한 `granted`는 서버 기기 등록이나 실제 수신의 증거가 아니다. 기기 구독은 서버에서 따로 확인하고, 등록이 진행 중일 때 UI 타임아웃으로 재시도를 열지 않는다. 조회만 시간 제한과 이전 응답 무시를 적용한다.
- 설치 안내 컴포넌트가 standalone에서 일찍 반환하면 그 안의 알림 설정도 숨겨진다. 설치 전후 공통 알림 영역을 유지하고, 설치 여부만 확인했을 때는 최신 버전까지 확인한 것으로 표시하지 않는다.

- `data-cocotrip-navigation=reload`는 새로고침 방식만 뜻한다. 이것만으로 서비스워커 자동 업데이트 성공을 판정하지 말고, 수동 새로고침 없는 이전→새 배포 버전 전환과 실제 Android 실행을 별도로 확인한다.
- 새 worktree는 Vercel 프로젝트 연결 정보가 없다. 이 상태에서 `vercel curl`을 먼저 실행하면 폴더명으로 빈 프로젝트를 만들 수 있으므로, 기존 CocoTrip Vercel 프로젝트에 먼저 link한 뒤 조회한다.
- Windows 서명 보관 폴더의 상속을 끈 뒤 새 로컬 파일을 만들면 접근 규칙이 비어 실행이 막힐 수 있다. 키·암호·실행기 생성 후 파일별 ACL과 실제 release 명령을 다시 확인한다.
- `verify:prepush`의 실수 패턴 검사는 `origin/main..HEAD`만 보므로 변경이 아직 커밋 전이면 `no changes`로 건너뛴다. 커밋 뒤 같은 검사를 다시 실행해야 근거가 된다.
- Android 의존성은 표시 이름을 좌표로 추측하지 않는다. 공식 Google Maven의 실제 groupId·artifactId·version과 POM/AAR 존재 여부를 확인한 뒤 고정한다.
- `/admin`에서는 고객용 프로모션·쿠키·가입 모달·하단 탭·하단 여백을 모두 격리하고, 운영에 필요한 PWA 업데이트 알림만 유지한다.
- Firebase `getIdToken`을 변수로 떼어 호출하면 `User`의 `this`가 깨질 수 있다. 반드시 `user.getIdToken()`으로 호출한다.
- Windows에서 `.bat`를 `shell: true`로 실행하면 공백·메타문자 경로가 깨지거나 명령 주입 위험이 생긴다. Java 실행 파일에 wrapper·도구 인수를 배열로 직접 전달한다.
- `apksigner`의 모든 실패를 미서명으로 간주하지 않는다. ZIP 무결성·`aapt2` 패키지명·정확한 종료 코드와 `DOES NOT VERIFY` 메시지를 모두 확인하고 하나라도 다르면 실패한다.
- 개인용 sideload도 실제 서명키·SHA-256·공개 `assetlinks.json`·서명된 release APK가 모두 없으면 출시할 수 없다.
- `bookings`, `pending_bookings`, `mood_bookings`는 같은 표의 복사본이 아니다. 한 컬렉션만 읽고 “전체 예약”이라고 표시하지 않는다.
- 고객 이름·이메일·전화번호·여행일이 같다는 이유로 예약을 합치지 않는다. 확정된 입금 대기 문서와 정식 예약의 주문·예약·캡처 식별자가 정확히 일치할 때만 mirror로 정리한다.
- `P0` 순위 값은 숫자 `0`이다. `rank || fallback`을 쓰면 `0`이 fallback으로 바뀌어 가장 긴급한 일이 뒤로 밀린다. 키 존재 여부를 따로 검사한다.
- 과거 `decision_queue` 문서에 `status`가 없으면 정규화 결과는 `pending`이다. 처리 대상 여부도 원본 값이 아니라 이 정규화된 상태로 판단한다.
- 원본 조회 실패를 `0건`으로 바꾸지 않는다. 성공한 원본은 계속 보여주되 실패한 원본과 부분 집계 상태를 화면에 명시한다.
- 재시도 큐 읽기가 실패했을 때 빈 배열을 집계 함수에 넘겨 `정상 · 대기 없음`으로 표시하지 않는다. 해당 자동화 카드도 `상태 확인 실패`로 닫아 둔다.
- 통합 화면은 읽기 전용이다. 예약·결제·환불·배차 상태를 바꾸는 API를 연결하지 않고, 응답에도 고객 개인정보를 싣지 않는다.
- GitHub 정기검사 실행 이력이 아직 연결되지 않았다면 정상으로 추정하지 않는다. `미연동`으로 표시하고 실제 Actions 화면으로 연결한다.
