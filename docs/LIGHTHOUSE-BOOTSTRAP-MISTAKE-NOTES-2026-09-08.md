# 보호된 미리보기 검사 도구 최초 설치

## 2026-09-28 스크롤 경고 위치 누락 원인

- 고정 Lighthouse 12.6.1은 `uses-passive-event-listeners`의 위치를 `source.line`·`source.column`으로 기록한다. 진단기는 `lineNumber`·`columnNumber`를 읽어 원격 경고의 줄·열을 버렸다. 실제 감사 구조로 회귀 검사를 고치고 기존 숫자 범위·원문 비노출을 유지했다.
- 이전 실행은 원본 보고서를 보관하지 않아 정확한 함수 위치를 소급 확인할 수 없다. 새 검사에서 위치가 나온 뒤 제품 코드를 수정한다. 로컬에서 찾은 `touchstart` 등록은 이미 `passive: true`여서 원인이라고 단정하지 않는다.

## 2026-09-28 사전 생성 HTML 재현과 검사 도구의 스레드 혼합 오류

- 제품 PR1421 `ab2dd11d`를 실제 설치된 사전 렌더러와 `PRERENDER=1`로 격리 빌드했다. 홈·투어·차터 HTML 감사 3/3 통과, 공개 API는 가짜 응답, 외부 통신은 차단했다. 기존 `PRERENDER=0` 검사와 달리 출처 미상 재계산 경고를 로컬에서도 재현했다. 데스크톱 성능 99/99/98은 이 합성 환경의 결과이며 운영 측정값이 아니다.
- 동일한 원본 trace에서 Lighthouse 12.6.1은 홈 `UpdateLayoutTree` 34.751ms를 강제 재계산으로 보고했다. 같은 프로세스·스레드의 부모는 `RunTask`뿐이고 JS 호출 부모가 없었다. 다른 스레드의 `v8.parseOnBackground`와 시간만 겹쳤다. 설치된 `WarningsHandler`가 스택을 스레드 구분 없이 공유하는 것이 원인이다. 원본 핸들러 재생은 정확히 같은 1건, 프로세스·스레드를 나눈 후보 재생은 0건이었다. 스타일 계산에 34.751ms가 걸린 사실 자체는 그대로다.
- `patch-lighthouse-reflow.mjs`는 검토된 CI 도구가 복제한 고정 배포본에만 적용한다. 원본 SHA-256이 다르면 중단하고, `pid:tid`별 스택·작업 상태만 분리한다. 30ms 기준과 다른 감사·실패 판정은 유지한다. 실제 같은 스레드의 강제 계산, 여러 작업, 경계값·누적, 초기화·긴 작업 보존을 실행 검사한 뒤에만 수집을 시작한다. 미지의 새 배포본에 문자열 패치를 억지 적용하지 않는다.
- 남은 원격 스크롤 경고의 위치를 식별하도록 고정된 스크립트 종류와 제한된 정수 줄·열만 진단에 추가한다. 원문 URL·파일명·쿼리·오류 본문은 출력하지 않고 기존 개수·판정은 유지한다. 브라우저에서 해당 Preview 접근은 확인됐다. 연결 도구의 403을 브라우저 로그인 실패로 단정하거나 재인증을 반복 요청하지 않는다.
- 이번 로컬 오판 재현으로 원격의 출처 미상 경고 전체, 미사용 CSS·JS, 스크롤 경고가 해결됐다고 주장하지 않는다. 전역 CSS는 초기 화면과 다른 경로가 공유하므로 근거 없이 삭제하지 않았다. 제품 파일·환경변수·인증·가격·보호 기준 변경과 운영 배포는 없다. 도구 PR을 검토·머지한 뒤 기존 제품 Preview에서 한 번 재검사해야 원격 결과가 확인된다.

오답노트: 출처 미상 성능 경고는 원본 trace의 프로세스·스레드와 실제 JS 부모를 확인한다. 사전 생성 HTML을 쓰는 배포를 빈 HTML 로컬 검사만으로 대신하지 않는다. 분석 도구의 오판 수정과 제품의 렌더링 비용 개선은 별개의 결과다.

## 2026-09-27 검사 증거 덮어쓰기와 경고 분류 누락

- PR1421의 가이드 목록 복귀 검사는 iPhone 14 Pro에서 한 번 실패하고 재시도로 통과했다. 그런데 순차 실행한 세 Playwright 명령이 같은 HTML 보고서와 테스트 출력 폴더를 덮어써 마지막 analytics/charter 결과만 아티팩트에 남았다. 각 명령의 두 출력 경로를 분리하고 기존 HTML 보고서 루트만 업로드한다. 실제 오프라인 실패 → 성공 실행 뒤 첫 보고서의 첨부 파일과 본문이 보존됨을 확인했다. 재시도·타임아웃·합격 기준은 바꾸지 않았다.
- Lighthouse 요약기는 고정된 `lighthouse:recommended` 규칙 중 일부 warn 항목과 로컬 `is-crawlable` warn 설정을 누락했다. 실제로 사용 중인 고정 배포본의 규칙과 대조해 정적 허용 목록을 보완했다. 이전 격리 로컬 결과의 미분류 19개는 캐시·화면 구성량·렌더링 지연·속도 관련 경고로 분류됐다(수정 후 unknown 0, suppressed 0). 이것이 PR1421의 원격 미분류 19개와 모두 같다는 뜻은 아니다.
- 동일한 항목·등급·실측값·기준값은 횟수로 합쳐 뒤의 진단이 잘리지 않게 했다. 출력 20개·입력 256개·횟수 99·숫자 범위 제한, 미등록 ID/주소/쿠키/본문 미출력, 실제 검사 판정과 실패 종료는 유지한다. 고정 배포본과 로컬 설정의 켜진 규칙은 모두 분류됨을 확인했다.
- 원격 iPhone 검사는 WebKit이다. Chromium에 아이폰 크기만 적용한 결과로 대신하지 않는다. 실제 WebKit 26.5의 iPhone 14 Pro 설정(화면 393×852, viewport 393×660)에서 수정 전·후 빌드를 각각 3회 확인해 가이드 복귀와 Article JSON-LD 제거가 정상임을 확인했다. 원격 일시 실패는 재현되지 않아 제품 코드나 대기시간을 추측으로 바꾸지 않았다.
- 진단 도구는 검토된 기본 브랜치에서만 실행한다. PR의 진단 코드를 비밀값과 함께 실행하도록 보호를 바꾸지 않는다. 이번 변경은 검사 증거 보존과 분류 보완이며, 성능 경고나 원격 가이드 실패의 제품 원인을 해결했다고 보고하지 않는다.

## 2026-09-27 전역 CSS의 죽은 가이드 규칙

- 실제 빌드 CSS는 256,906 → 255,943바이트, gzip 41,301 → 41,045바이트로 줄었다(압축 절감 256바이트). 큰 미사용 JS 문제의 해결로 확대 해석하지 않는다. 가이드 계약·렌더 검사 48개, 격리 dev 4경로 × 데스크톱/모바일 8화면을 확인했다.
- 검사 주의: 가이드의 `/blog-images/*`는 Vercel에서 공개 이미지 제공 API로 연결되므로 로컬 `public`에 없을 수 있다. 단순 HTTP 200은 이미지 성공의 근거가 아니다. 이번 공개 이미지 2개는 운영에서 `image/webp`로 정상 응답했고, 로컬 검사는 해당 공개 자산을 경계에서 대체한 뒤 `img.decode()`까지 확인했다. HTML 폴백을 이미지로 수용한 첫 검사 장치를 수정했으며 제품 이미지·경로는 바꾸지 않았다.

- `src/main.tsx`가 `src/index.css`를 시작 시 전역으로 불러오는데, 그 안의 `.guide-article` 본문 규칙은 이전 클래스에 묶여 더는 적용되지 않았다. 실제 본문은 `GuideArticleBody.tsx`에서 `.ec-prose`를 쓰고, 전용 `guide-editorial.css`는 lazy `/guide` 경로에서만 로드된다.
- 확인된 14개 옛 선택자만 제거하고 기존 editorial guide 단위 계약에 “전역 `.guide-article`은 없고 `.ec-prose`는 유지” 검사를 추가했다. 이로써 세 초기 경로가 불필요하게 받던 일부 CSS를 줄인다.
- Lighthouse 기록은 경로마다 미사용 CSS 항목 1개를 보여주지만 이 옛 규칙이 그 항목의 전부인지는 밝히지 않으므로, 전체 CSS 기준을 해결했다고 단정하지 않는다. 초기 JS·요청 의존성의 Firebase 경로와 미확정 스크롤/리플로우 원인은 별도이며 이 수정 범위에서 바꾸지 않았다.

## 2026-09-24 보호된 설치 설정 파일의 쿠키 누락

- main의 진단 수정(PR1418) 후 검사 35969794949 첫 실행은 수집 단계에서 중단됐다. 한 번 재실행하자 세 경로 수집이 완료됐고, 각 경로에서 CORS 2건·리소스 로드 오류 2건이 확인됐다. HTTP 400–599 요청은 없었다. 최초 수집 실패를 페이지 결함으로 계산하거나 재시도 성공을 정책 통과로 보고하지 않는다.
- 현재 빌드가 만드는 `<link rel="manifest">`에는 쿠키 전달 설정이 없었다. 실제 Chromium과 루프백 서버 두 개로 재현한 결과, 기존 태그는 이미 가진 HttpOnly 쿠키를 전달하지 않아 인증 화면으로 리디렉션되고 CORS 오류가 발생했다. 같은 태그에 `crossorigin="use-credentials"`를 적용하면 쿠키가 전달되고 리디렉션·CORS 오류가 모두 사라졌다. 실제 운영 인증값이나 고객 데이터는 사용하지 않았다.
- 이미 설치된 VitePWA의 `useCredentials: true` 옵션으로 빌드 태그를 수정한다. CocoTrip·MOOD·오너 설정 파일 경로는 모두 같은 출처의 고정 경로이며 기존 ManifestSwitcher는 해당 속성을 보존한다. 인증 우회, CORS 허용 범위 확대, 미리보기 보호 해제, 쿠키·키 발급은 하지 않는다. 근거: [Vite PWA 공식 FAQ](https://vite-pwa-org.netlify.app/guide/faq#web-app-manifest-and-401-status-code-unauthorized).
- 스크롤 경고는 세 경로 모두 미리보기와 같은 출처 1건으로 확인됐지만 정확한 함수는 미확정이다. 같은 출처라는 사실만으로 제품 코드와 미리보기에 주입된 스크립트를 구분할 수 없다. 직접 등록한 PWA 입력 감지와 React의 스크롤 관련 이벤트는 이미 passive를 사용하므로 추측으로 변경하지 않는다.
- 미사용 CSS·JS, 요청 의존성, Preview 색인 차단, 변동하는 출처 미상 리플로우와 미분류 판정은 별도 잔여 항목이다. 로컬 쿠키 재현 통과가 원격 CORS 전체 해소나 실제 설치·업데이트·문의 저장·결제 성공을 증명하지 않는다. 원격 적용 후 동일 검사로 따로 대조한다.
- 회귀 검사는 `npm run build` 후 `npx playwright test tests/e2e/manifest-cookie-credentials.spec.ts --project="Desktop Chrome" --workers=1 --reporter=line`으로 실행한다. 실제 생성된 HTML 태그를 사용하고 쿠키 누락 대조군의 실패와 수정군의 성공을 한 검사에서 확인했다(1개 통과). 모든 요청은 루프백 두 출처로 제한한다. 기존 PWA 검사 38개와 격리 dev 홈·MOOD 화면/인트로 자산도 통과했다.

오답노트: 인증 쿠키가 브라우저에 있어도 manifest 요청은 기본적으로 쿠키를 보내지 않는다. 보호를 끄는 대신 정상 요청에 필요한 속성을 사용한다. 검사 장치도 화면의 숨겨진 첫 링크나 임의 글자 수가 아니라 해당 화면의 실제 표시 요소를 기준으로 판정한다. 루프백 전용 E2E도 공용 analytics-guard의 test/context를 사용한다. 최초 푸시 전 P272가 직접 import를 차단했고, 공용 도구를 실제로 사용하도록 수정한 뒤 브라우저 재검사와 오답 린트가 통과했다.

## 2026-09-24 스크롤 경고 출처 판독 수정

- 고정 Lighthouse 12.6.1의 `uses-passive-event-listeners`는 출처를 `details.items[].source.url`에 저장한다. 기존 요약기는 이 필드를 읽지 않아 실제 출처가 있어도 `unknown`으로 분류했다. 설치된 audit 구현과 같은 구조의 회귀 검사로 수정했다.
- 콘솔 오류는 고정 오류 종류만, 실패 요청은 제한된 출처·요청 종류·HTTP 오류 상태와 개수만 요약한다. 원문 메시지·URL·헤더·쿠키를 출력하지 않고 기존 판정·보호 규칙을 유지한다. 이 수정은 실패 원인을 읽기 위한 것이며 제품 오류 해결이나 점수 통과를 뜻하지 않는다.
- 운영 배포의 실제 정적 HTML·JS를 새 브라우저에서 실행하고 API를 가짜 응답으로 바꿔 세 경로를 확인했다. 인증·DB·분석·지도·결제·발송 요청과 WebSocket은 통과시키지 않았다. 콘솔 오류·실패 요청·예외는 없었고, Lighthouse와 같은 CDP 위반 수집에서도 경고가 재현되지 않았다. 서비스워커 차단에 따른 검사 장치 경고는 제품 결함으로 계산하지 않는다.
- Vercel 연결 도구는 보호된 미리보기 접근을 거부했다. 연결 권한 갱신을 요청하면서 기존의 검토된 main 도구를 사용하는 검사 경로를 유지한다. 원문 오류가 없는 상태에서 콘솔 오류를 특정 API나 Vercel 도구 모음 탓으로 단정하지 않는다.

오답노트: 보고서의 실제 항목 구조를 먼저 확인한다. `sourceLocation.url`과 `source.url`은 서로 다른 audit의 필드이며, 출처를 읽지 못한 상태를 출처가 없다는 증거로 사용하지 않는다.

- 비활성 Sentry의 수동 오류 보고 함수에도 운영 모드·DSN 조건을 적용해 빌드가 불필요한 SDK 코드를 제거하게 했다. 활성 상태에서는 기존 동기 초기화를 유지하고, 기존 오류 필터·개인정보 마스킹을 보존한다. 초기화·보고 실패가 앱으로 전파되지 않고 초기화 전 보고가 실행되지 않도록 확인했다.
