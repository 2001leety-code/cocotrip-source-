# 공개 화면 접근성·사진·초기 로딩 개선 검증

## 승인과 안전 경계

운영자는 공개 화면의 사진·접근성·글꼴·초기 로딩으로 범위를 넓히는 실행안에 2026-09-07 "계속해"로 승인했다. 기존 PR #1380에 묶는다. 인증·결제 규칙, 실제 고객 자료, 환경변수 값, 실제 알림 활성화는 변경하지 않는다. Lighthouse 점수와 개별 필수 검사 기준도 낮추지 않는다.

이 문서는 이번 공개 화면 변경에 관한 기록이다. 개인용 Android 컨트롤러의 실제 로그인·알림 수신·PC OFF·서비스워커 업데이트 완료를 뜻하지 않는다.

## 실제 원인과 수정

- 홈과 투어 카드가 화면보다 훨씬 큰 사진 원본을 받았다. 기존 사진은 보존하고 화면 크기에 맞는 파생 사진을 제공한다. 생성 자료의 해시·크기·인코더 정보는 도구용 기록에 두고, 방문자용 자료에는 필요한 경로·치수만 둔다. 작은 공용 로고는 별도 자료로 분리해 모든 사진 목록을 첫 화면에 끌어오지 않는다.
- 공용 HTML에 과거 홈의 배경 사진 preload가 남아, 현재 사용하지 않는 사진을 다른 페이지에서도 받았다. 해당 preload만 제거하며 사진 원본·PWA 인트로·아이콘은 보존한다.
- 모든 방문자가 PDF용 CJK 세 글꼴의 외부 CSS를 기다렸다. 웹은 기존 기기 글꼴 목록으로 표시하고, PDF 다운로드 때만 같은 Noto 글꼴을 준비한다. 실제 문자의 보통·굵은 글꼴 및 `fonts.ready` 확인에 실패하면 캡처를 중단한다. 고객 문자를 URL에 담지 않는다.
- 로고/언어/지역 버튼의 접근성 이름이 보이는 글자와 달랐고, 단계 버튼에 목록 항목 역할을 덮어썼다. 표시와 이름을 맞추고 목록과 버튼 역할을 분리했다. 설명목록의 `dt`/`dd` 순서를 복구하며 CSS 표시 순서는 유지했다.
- 출발지·견적 안내의 중첩된 투명도 때문에 글자가 흐렸다. 기존 색상 체계에서 대비를 높였다. 공연의 지도 링크는 선택 버튼 밖으로 분리했다. 공연을 실제 선택한 뒤 드러나는 인원 +/− 및 승차장 버튼에도 이름·44px·키보드 초점을 보완했다. 금액 계산과 예약 전달 값은 그대로다.
- 검색창 전체를 첫 방문 때 불러오던 경로를 요청 시 로딩으로 분리했다. 독립 검토에서 청크 실패가 전역 오류 화면으로 전파되어 작성 내용을 지우는 경우를 재현한 뒤, 검색 영역 안에서만 실패를 처리하도록 고쳤다. 늦은 로딩 중 본문에 다시 입력하면 검색 열기를 취소하며, 닫을 때 다른 입력칸의 초점을 빼앗지 않는다. 실제 Chrome의 실패/재시도/빠른 닫기/두 가지 본문 재입력/정상 Radix 초점 복귀를 가짜 자료로 확인했다.

검색 재시도의 한계: Chrome은 실패한 모듈을 현재 문서 안에서 기억할 수 있다. 새 lazy 인스턴스로 시도하더라도 네트워크 재요청 없이 실패한 실브라우저 사례를 확인했다. 따라서 재시도 성공을 보장하지 않으며, 오류 상태를 닫고 작성 내용을 보관한 뒤 사용자가 페이지를 다시 열도록 안내한다. 강제 새로고침이나 캐시 우회 URL을 추가하지 않는다.

## 검증 방식

1. 기존 운영 사이트 보고서: `/`, `/tours`, `/charter`, 고정 Lighthouse 12.6.1 / LHCI 0.15.1, 데스크톱 각 1회. 원본은 별도 임시 폴더에 보존했다.
2. 수정 전 main과 수정 후 후보를 같은 가짜 Firebase 설정으로 각각 `npm run build`한 뒤 로컬 미리보기에서 같은 검사 설정으로 비교한다. 로컬 속도를 운영 속도로 표시하지 않는다. 기존 설정의 성능 점수 경고와 개별 필수 검사 오류를 따로 센다.
3. 실제 개발 브라우저에서 검색 입력/키보드 이동, 지역 선택/해제, 출발지 선택→다음→키보드 복귀, 네 언어 전환, 공연 선택 뒤 버튼을 확인한다. 화면 폭은 요청값뿐 아니라 실제 `innerWidth`로 확인한다. 이 기기의 120% 배율 때문에 도구에 390을 요청하면 실제 CSS 폭은 325가 되어, 실제 390/1280이 되도록 조정했다.
4. PDF: 가짜 최소 플랜을 사용한 한·영·일·중 실제 클라이언트 다운로드 및 모든 페이지 이미지 검사. 정상/글꼴 차단을 나눠 확인한다. 업무 API와 실제 고객 자료는 사용하지 않는다.
5. 전체 단위 검사·변경 파일 린트·빌드·플랜 오프라인 하네스·언어 키·용량·PWA 잠금·개발 하네스 배제 확인 후 한 번에 푸시한다.

## 확인된 중간 결과 — 최종 판정 아님

첫 후보 빌드(사진 후속 압축/검색 실패 보호 이전)의 로컬 접근성은 세 경로 모두 100, 콘솔 오류 감사는 모두 통과했다. 홈/투어/차량 성능은 각각 93/89/91이었다. 이는 운영 사이트 80/77/81과 실행 위치가 다르므로 개선 점수 차이로 주장하지 않는다.

이 후보에도 공용 JavaScript·CSS·요청 연결 및 일부 사진 크기 필수 오류가 남았다. 단순한 성능 점수 통과를 전체 통과로 세지 않았다.

PDF 정상 생성은 네 언어 모두 한 페이지, 실제 글꼴 3종×2두께 확인 완료. 글꼴 CSS 차단 시 다운로드·캔버스·PDF 라이브러리 로드·남은 로딩 요소가 모두 0이었다. 가짜 최소 플랜 검사이므로 실제 고객 플랜 내용의 정확성까지 증명하지 않는다.

## 남은 구조적 문제와 출시 경계

`lighthouse:recommended`의 `unused-javascript`는 개별 파일의 미사용 추정량 20KiB 초과 항목이 **0개**여야 통과한다. 현재 React 자체도 이 기준에 걸리며 Firebase 단일 파일만 나눠 해결되지 않는다. Header의 위시리스트·장바구니·등급·푸시 등록과 홈의 다음 여행 훅에도 정적 Firestore 경로가 있다. 실제 초기화/구독 시점을 바꾸는 작업은 별도 설계가 필요하다. 작은 조각으로 나눠 경고만 없애는 방식은 개선으로 계산하지 않는다.
